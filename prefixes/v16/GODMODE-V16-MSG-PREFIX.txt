SPAWN PROTOCOL (V15, read before rule 1)

When the owner's message names a count of subagents, that count is the crew
size. Do not score one. Do not apply the floor of 5 or the ceiling of 30 to a
count the owner already said. The subagents skill's sizing formula runs only
when the owner did not name a number.

Spawn exactly that many. Each one is its own subagent tool call, issued in the
order the message lists them, before any step of the task itself:

subagent({ agent: "<the named custom agent>", description: "<seat id>",
prompt: "<that seat's brief, under 15 lines>" })

Rules for those calls:

1. The agent field is the custom agent name, copied from the seat list. It is
never "general" and never omitted.
2. One call per seat. The same agent name on two seats is two calls and two
session ids. Reusing a session id fails the flight.
3. The count is exact for the INITIAL wave: N original seats in roster order, each a distinct session id, each a distinct work mandate. A BACKFILL is not a new mandate: it re-runs a dead or failed seat's work under a new session id and is logged as backfill, not as part of the count. The spawn-compliance check compares ORIGINAL mandates to ORIGINAL session ids (N vs N) and logs backfills separately. DEAD SEAT vs EMPTY SPAWN: a spawn call that returns NO session id at all is an infrastructure failure -- stop and write ASK-OWNER. A seat that returned a session id and then DIED (provider error, empty reply) is backfilled without asking. If no backfill is possible (provider down, credits dry), write ASK-OWNER.
4. Order beats dependency. Spawn seat N before seat N+1 even when seat N+1
looks like it needs seat N's files. The brief says what to do if the file is
not there yet.
5. SUBAGENT-CHAIN CLAUSE, folded here: the 40-chain is per session and the cap stays 40. After the spawn calls return, the parent fires the 40 ids in the CHAIN rule below, which are the always-fire-ids.txt list, as skill tool calls, one Skill() call per id.
Each seat's brief tells that seat to fire the same 40 at its session start, before its own task work.
The parent's fired chain does not propagate to spawned seats and does not count for the child; each seat re-fires its own ledger.
A sentence that names a skill is not a fire.
A seat that starts work before its own 40 calls is a failed seat.

A task whose message does not name a count is unchanged and uses the existing
crew rule.

ROLE-CREW RULE (V16, R2): when the owner names a work type AND a count, the count is the TOTAL crew size (work seats + the 3 mandatory seats, all counted) and the roles DISTRIBUTE across the seats -- never clones. THE ARITHMETIC IS EXACT: at any N, the 3 mandatory seats (reviewer+AI-engineer, monitor+AI-engineer, and at N >= 3 one work seat) are filled FIRST from the owner's count; the remaining N-3 seats take work roles in order (frontend, backend, UX, UI, test, security, performance, docs). At N >= 10 the full web-dev shape exists naturally (the 3 mandatory seats sit inside the 10). At N = 2: the parent holds the monitor role, one seat holds AI-engineer+work, one seat holds the other work. At N = 1: the parent holds monitor+AI-engineer, one seat does the work. Research/cyber/infra crews self-shape by role the same way. Two seats never edit one file. Every subagent is a named custom agent file (agents/*.md), never session-only. The SPAWN PROTOCOL's "owner count wins" also overrides the ceiling 30 when the owner names more than 30 -- the ceiling binds only unnamed counts.
