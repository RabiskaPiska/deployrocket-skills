# prompt-preflight - the pre-execution validator for executor prompts

You are running **prompt-preflight**. A generated executor prompt (from the `/prompt`
factory, a promptgod rewrite, a repair-wave corrective prompt, or any hand-built dispatch)
is about to be sent to a spawned subagent. Your job: validate it AGAINST THE MEASURED
FAILURE CLASSES of this campaign before one token of dispatch budget is spent on a prompt
that is structurally guaranteed to fail.

**Core law:** a prompt defect caught here costs one edit. The same defect caught after
dispatch costs a wasted spawn, a wasted retry wave, a corrupted results file, and a
recovery-engineer seat. Preflight is the cheapest gate in the entire pipeline.

---

## 0) WHY THIS EXISTS - the measured failure classes

Every check in this skill maps to a failure that was actually observed and measured during
the goal-godmode-v65-fleet campaign (2026-11). These are not theoretical lint rules.

| # | Failure class | What it cost when missed | Gate |
|---|---------------|--------------------------|------|
| F1 | Wrong model-ref shape in the spawn payload | `provider.no-route` SILENT failure - the session is created, the child answers with a model the caller never asked for, no error surfaces anywhere | Gate A1 |
| F2 | Assuming a spawned child can spawn its own subagents | depth-1 spawn limit: `Subagent depth limit reached` + injected DENY on the spawn tool; the child stalls or hallucinates a crew it cannot create | Gate A2 |
| F3 | Reading only page 1 of a cursor-paginated endpoint | 50/page cap: 92-message session read as 0 skill fires; verdicts computed on a silent 42-message tail loss (P8 root cause) | Gate A3 |
| F4 | Appending content after the gates line | the gates line MUST be the LAST line of the turn; any excerpt that ends mid-section or with trailing prose makes the gate scan mis-parse the turn as ungated | Gate A4 |
| F5 | Assuming the spawn error would be loud | `provider.no-route` returns HTTP 200 with a normal-looking session; the failure is only visible by diffing the child's actual model against the requested one | Gate A5 |
| F6 | PowerShell 5.1 parsing em-dashes / curly quotes in pasted prompt text | byte 0x97 (cp1252 em-dash) instead of UTF-8 E2 80 94; parse errors, mojibake in delivered files (D-L3 finding) | Gate B1 |
| F7 | `$ErrorActionPreference='Stop'` turning ordinary native stderr into a fatal `NativeCommandError` | healthy commands (curl progress, git fetch chatter) abort the script mid-run | Gate B2 |
| F8 | `${VAR}` non-expansion in opencode 2.2.6 prompt text | literal `${VAR}` reaches the child; the child invents a value; the whole downstream step runs against the wrong name | Gate B3 |
| F9 | Serve password read once and cached across a restart | the serve rotates its password on every restart (`LAST 'server password ' line` of the serve log is the ONLY valid source at call time); cached creds return 401 and look like an outage | Gate B4 |
| F10 | Padding: filler lines to hit a line-count target | a 1,332-line skill whose tail was ~300 identical `<!-- padding -->` lines; audits flag it, juries deduct it | Gate C1 |

**Preflight the mistake-memory first (Step 0 of every run):** grep the runlogs and root-cause
notes for the symptom class you are about to validate against. A hit is either a known fix
(use it) or a banned option (already failed). This skill's checklist IS that memory,
materialized.

---

## 1) WHEN IT FIRES

**Always-fire trigger - run the full Gate A-D pass when ANY of these is true:**

- A prompt generated by the `/prompt` factory is about to be dispatched to a subagent.
- A `subagent(...)` spawn call is about to be emitted with a hand-written or hand-patched prompt.
- A recovery-engineer seat has designed a corrective prompt (repair wave) and is about to
  launch the repair spawn.
- A prompt file was edited after its last successful preflight (edit invalidates the pass).
- The word "dispatch", "spawn wave", "executor prompt", or "repair wave" appears in the plan.

**Skip conditions (report as `skipped: why`, never silent):**

- The turn dispatches no prompt to any spawned session (pure local tool work).
- The prompt is a re-send of a byte-identical payload that already PASSED preflight this
  session and has not been edited (idempotency rule, Section 10).

## 2) INPUTS AND OUTPUTS

**Inputs (all must be present before validation; missing input = auto REJECT, not a guess):**

| Input | Source | Required? |
|-------|--------|-----------|
| The full prompt text (exact bytes that will be dispatched) | prompt factory output, repair-wave schema, or the spawn call's `prompt` field | YES |
| The spawn payload (agent id, model ref, background flag, sessionID if resuming) | the orchestrator's spawn plan / tasklist | Required for Gate A |
| The tasklist (seat table: ID / IN / OUT / deliverable / wave) | `subagents` skill S3 output file | Required for Gate D |
| Target runtime + version (e.g. opencode 2.2.6 serve, PowerShell 5.1, bash on VPS) | environment probe or the dispatch plan itself | Required for Gate B |
| Expected outcome statement (what "done" looks like for this dispatch) | the goal / spec file | Required for verdict |

**Outputs:**

1. A **preflight verdict record** (Section 9 format): `PASS`, `PASS-WITH-FIXES`, or `REJECT`,
   with per-gate evidence.
2. On `PASS-WITH-FIXES`: the exact minimal edits, already applied to the prompt text, listed
   one per line as `FIX: <gate> -> <edit>`.
3. An entry appended to the run's log: timestamp, prompt hash (sha256, first 16 hex), verdict,
   fix list. The hash makes re-runs idempotent (Section 10).

---

## 3) THE PROCEDURE - six steps, in order, no reordering

```
Step 1  Freeze the artifact    : hash the exact prompt bytes about to be dispatched.
Step 2  Gate A                 : spawn-payload schema checklist (A1-A6). One finding = one fix.
Step 3  Gate B                 : per-runtime known-failure checklist (B1-B6).
Step 4  Gate C                 : AI-slop detection (C1-C6). Any hit = rewrite, not patch.
Step 5  Gate D                 : seat-disjointness validation (tasklist-first).
Step 6  Verdict                : PASS / PASS-WITH-FIXES / REJECT + evidence, per Section 9.
```

Rules that apply to all gates:

- **Validate the bytes, not the intent.** Run the detection commands (Section 5, Section 6)
  against the actual prompt file. Reasoning-only validation caps the whole preflight at
  "UNVERIFIED" - report it that way.
- **One finding = one evidence line.** `Gate B1 FAIL: line 214 contains U+2014 em-dash`
  is a finding. `prompt looks Windows-unsafe` is not.
- **A gate that cannot run is a finding, not a pass.** If you cannot check cursor handling
  because the endpoint is unknown, the verdict is `PASS-WITH-FIXES` at best, with the
  unknown named.

## 4) GATE A - SPAWN-PAYLOAD SCHEMA CHECKLIST

The spawn payload is a contract with the runtime. The runtime does not warn when the
contract is violated in the six ways below. Check every one, in order.

### A1 - Model-ref shape (providerID + id, exactly)

The known-good shape is `providerID/modelID` - one slash, both parts non-empty, matching a
model the provider actually serves. Measured-good example from this campaign:

```
abliteratedllm/glm-5.3-flash-abliterated     <- correct: providerID/id
```

Failure variants (each produced a silent or confusing failure this campaign):

| Variant | Symptom |
|---------|---------|
| `id` only (`glm-5.3-flash-abliterated`) | provider.no-route - session spawns on a fallback or errors silently |
| `provider/id#variant` with the wrong variant token | seat runs an unintended variant; model lineage in the proof is corrupted |
| empty / omitted model field on the spawn | child silently inherits the parent's (often most expensive) session model |
| trailing whitespace or a BOM inside the ref string | route lookup misses; silent fallback |
| a model name the parent *recalled* instead of looked up | provider.no-route; the child answers on whatever the runtime picks |

**Detect (before every spawn, mechanically):**

```
1. Resolve the intended model via the models/agent catalog tool - never from memory.
2. Assert the spawn payload's model string contains exactly one "/".
3. Assert both halves are non-empty and trimmed.
4. If the runtime supports variant syntax, assert the variant is one the provider lists.
```

**Why "silent" matters:** `provider.no-route` does not raise. The session is created, the
child runs, the final message arrives. The ONLY detection is post-hoc: read the child's
actual model from the session record and diff it against the requested ref. Preflight
therefore also mandates the post-spawn check in A5.

### A2 - Depth-1 spawn limits (children cannot spawn)

OpenCode's `subagent_depth` defaults to 1. A spawned child that its prompt tells to
"spawn a verification subagent" or "fan out to researchers" will hit
`Subagent depth limit reached` and receive an injected DENY on the spawn tool.

**Checklist items for the prompt under validation:**

- [ ] The prompt contains NO instruction that requires the child to spawn sub-subagents.
- [ ] Any sentence like "delegate X to a subagent" or "spawn a crew" is removed or rewritten
      to "perform X yourself, serially".
- [ ] The prompt carries the standard line: do NOT spawn your own subagents - you ARE the
      implementer; the orchestrator owns merge and review.
- [ ] If the parent intends a fan-out, the fan-out is described as MULTIPLE sibling spawns
      from the ORCHESTRATOR, not as one mega-child with an internal crew.

**Detect:** grep the prompt text for `spawn`, `subagent`, `crew`, `delegate`, `fan out`.
Every hit must be either (a) describing what the ORCHESTRATOR already did, past tense, or
(b) an explicit prohibition. Any hit that assigns future spawning to the child = FAIL item.

### A3 - Cursor-pagination caps (50/page)

Any step in the prompt that reads sessions, messages, or list endpoints via the serve REST
API must follow the cursor. The campaign-measured shape:

```
GET /api/session/{sid}/message  ->  {"data": [...up to 50...], "cursor": {"previous": .., "next": ..}}
```

Page-1-only reads silently drop everything past 50 messages. The P8 finding: a 92-message
session audited as "0 skill fires" from page 1, when the full traversal showed 6.

**Checklist items:**

- [ ] Every list/read step either follows `cursor.next` until absent, or the prompt states
      AND the verdict accepts that only the first 50 items are in scope.
- [ ] Any pagination loop has BOTH a termination check (empty/absent cursor) AND a hard
      bound (max pages), because an unbounded cursor loop leaked 19.8 GB RSS on one
      diagnostic (PROOFFIN finding). No bound = reject the step.
- [ ] Counts claimed by the prompt ("verify all N messages") must be computed over ALL
      pages, never over `len(data)` of one response.

### A4 - Excerpt-tail anchoring (the gates line is the LAST line)

Gate-scan tooling reads the tail of a session's final message to find the gates line.
The contract: **the gates line is the LAST line of the turn.** If the executor prompt
instructs the child to end with anything else - a JSON block, a signature, a footer, a
"thank you" line - the scanner mis-parses the turn and reports the run as ungated.

**Checklist items:**

- [ ] The prompt's output contract says, verbatim or equivalent: "the gates line is the
      LAST line of your final message - nothing after it."
- [ ] No step appends content AFTER the gates line (no trailing JSON, no closing fence).
- [ ] If the deliverable requires a JSON final block AND a gates line, the JSON block comes
      first, the gates line last. When the orchestrator's parser needs the JSON last instead,
      that conflict is resolved BEFORE dispatch by the orchestrator's own contract - never
      by hoping the scanner tolerates one order.
- [ ] The prompt does not instruct the child to "end with a summary" after the gates line.

### A5 - provider.no-route silent failures (detect AFTER spawn)

Because no-route fails silently (A1), every dispatch plan must include the verification
step that would catch it:

- [ ] After the child's first reply lands, read the session record and assert the child's
      model equals the requested `providerID/modelID`.
- [ ] If they differ: this is a no-route or override event. Do NOT treat the child's answer
      as the requested model's answer. Re-spawn with the corrected ref, or accept and
      ANNOTATE the run that the model differed (the PROVIDER-TRUTH finding: seat sessions
      silently ran a different model because the launching parent selected one).
- [ ] The prompt itself cannot fix this - it is a spawn-call-side check. Preflight verifies
      the CHECK EXISTS in the plan; a plan without the post-spawn model assertion = finding.

### A6 - Spawn-payload field checklist (one table, run it every time)

| # | Field / property | Required | Failure mode if wrong |
|---|------------------|----------|----------------------|
| 1 | `agent` | valid agent id, quoted exactly | unknown-agent error or fallback type |
| 2 | model ref | `providerID/modelID`, resolved this session (A1) | provider.no-route silent |
| 3 | `description` | 3-5 words, present | UI/log ambiguity only |
| 4 | `prompt` | self-contained; NO session history paste | 40k-char blob buries the task (measured) |
| 5 | `background` | set deliberately, not by default | slow builds block the wave via slowest-child |
| 6 | `sessionID` | present ONLY when resuming; NEVER the parent's own id | resume of parent = corrupted context |
| 7 | sibling scope list | present in prompt (dedup enforcement) | duplicate-scope agents (Rule 2 violation) |
| 8 | evidence rule | "paste real tool results; no tool run -> [UNVERIFIED]" | unverifiable child claims |
| 9 | OUT + deliverable | explicit, named file or JSON block | silent finisher; merge has nothing to merge |
| 10 | gates contract | gates line is the LAST line (A4) | mis-parsed as ungated turn |
| 11 | no secrets in prompt | zero credentials inside mandates | leaked keys in logs |
| 12 | depth honesty | no child-spawning instructions (A2) | depth-limit stall |

**Gate A verdict:** PASS only if all 12 rows check. Each failed row gets a minimal fix and
moves the overall verdict to PASS-WITH-FIXES; a structural failure (rows 2, 4, 6, 10) that
cannot be fixed by edit = REJECT.

## 5) GATE B - PER-RUNTIME KNOWN-FAILURE CHECKLIST

These are the runtime-level traps that eat executor prompts on this fleet. Each entry is
symptom -> root cause -> detect -> fix. If the dispatch path touches the named runtime,
the row is mandatory; if it cannot apply, justify N/A in one line.

### B1 - PowerShell 5.1: em-dash and curly-quote parsing

- **Symptom:** a prompt or script containing an em-dash or typographic quote breaks when
  written/read through PowerShell 5.1; bytes arrive as 0x97 (cp1252) instead of UTF-8
  E2 80 94; downstream parsers, hash checks and YAML readers fail on "corrupt" files.
- **Root cause:** PS 5.1 default encodings (console + `Out-File`) are not UTF-8; the em-dash
  U+2014 and curly quotes U+2018/2019/201C/201D do not survive a cp1252 round-trip.
  Measured: MANIFEST-INPUTS.md carried byte 0x97 where a UTF-8 em-dash belonged (D-L3).
- **Detect:**
  ```
  # bytes-level, never console-level (console display lies):
  python -c "d=open(r'<file>','rb').read(); print('0x97 present:', b'\x97' in d); print('em-dash utf8 present:', b'\xe2\x80\x94' in d)"
  # any non-ASCII byte at all (for prompts that must be ASCII-safe):
  python -c "d=open(r'<file>','rb').read(); bad=[b for b in d if b>127]; print(len(bad),'non-ascii bytes')"
  ```
- **Fix:** author prompts ASCII-only (hyphen `-` for dashes, straight quotes). If a file
  must carry a real em-dash, write it from Python with explicit UTF-8, never through a
  PowerShell here-string. Patch single bytes, verify by re-read, and record the fix in the
  runlog.
- **Prompt-side rule:** an executor prompt that says "write the file with this content"
  must either guarantee ASCII content or specify the exact writing mechanism (python with
  encoding='utf-8'), never "use PowerShell here-string".

### B2 - `$ErrorActionPreference='Stop'` + stderr = NativeCommandError

- **Symptom:** a wrapper script with `$ErrorActionPreference='Stop'` dies partway through a
  healthy command sequence; the killer is an external tool (curl, git, ssh) writing ordinary
  progress to stderr.
- **Root cause:** under `Stop`, PowerShell 5.1 promotes native stderr output to a
  `NativeCommandError` record in certain redirection/host configurations, and a Stop
  preference treats the first record as terminating.
- **Detect:** any wrapper script that (a) sets `Stop`, AND (b) invokes native tools, AND
  (c) redirects or merges stderr, is suspect. Test: run the wrapper against a deliberately
  chatty native command; if it dies on the first stderr line, confirmed.
- **Fix:** scope `$ErrorActionPreference='Continue'` around native invocations (or drop
  `2>&1` merging), and rely on explicit `$LASTEXITCODE` checks for control flow instead.
- **Prompt-side rule:** executor prompts that ship PowerShell snippets must not combine
  global `Stop` with stderr-noisy natives; require `$LASTEXITCODE` checks.

### B3 - `${VAR}` non-expansion in opencode 2.2.6 prompt text

- **Symptom:** the child receives the literal string `${WORKSPACE}` / `${VAR}` in its
  prompt instead of the environment value; the child then guesses a value and proceeds -
  the worst failure mode because nothing errors.
- **Root cause:** opencode 2.2.6 does not expand `${VAR}`-style references inside prompt
  text at dispatch time; interpolation happens in some contexts (scripts, env blocks) and
  not in others, so a prompt that works when pasted into a shell silently degrades when
  sent through the API.
- **Detect:** grep the dispatch payload for `${` - every occurrence is either (a) inside a
  script the CHILD will write and execute (intended, fine) or (b) part of the prompt prose
  the parent expected the runtime to fill (broken).
- **Fix:** the parent resolves the value and inlines it before dispatch. A prompt that must
  carry a parameterized script keeps `${...}` inside a fenced code block clearly marked
  "literal, child expands at runtime".
- **Campaign provenance:** the `bootstrap-patched.ps1` dollar-guard comment ("${VAR} env
  passthrough is intentional") exists precisely because this class bit the fleet once.

### B4 - serve password rotation on restart

- **Symptom:** REST harvest / spawn scripts suddenly return 401 across the board after a
  serve restart; looks like the orchestrator is down; it is not.
- **Root cause:** the opencode serve generates a NEW password on every restart, logged as
  the LAST line matching `^server password ` in the serve log (`/tmp/oc-serve*.log`). Any
  credential cached from a previous run is stale.
- **Detect:** any credential source in a prompt or script that is not "read the LAST
  matching line of the freshest serve log AT CALL TIME" is a defect. Cached creds, creds in
  a prompt constant, creds in an env file older than the last restart: all fail this row.
- **Fix:** every prompt that instructs REST work carries the live-read rule: parse creds
  from the freshest `/tmp/oc-serve*.log` at call time; Basic auth `opencode:<password>`
  (NOT Bearer - measured gotcha); never hardcode.
- **Bonus check in the same family:** Basic auth header is `opencode:<password>`; a prompt
  telling the child to use a Bearer token repeats a measured failure.

### B5 - Exit codes read through a pipe / through formatting layers

- **Symptom:** "the gate returned 0" on a run that actually rejected the push.
- **Root cause:** piping a checker into `tail`/`Select-Object` or capturing via a wrapper
  surfaces the LAST command's exit code, not the checker's.
- **Detect:** any verification step in the prompt that pipes the gate/checker output must
  preserve `$?` / `$LASTEXITCODE` of the checker itself (or use `PIPESTATUS` on bash).
- **Fix:** run the checker unpiped for the verdict; pipe only for display afterwards.

### B6 - Script delivery: file, never inline

- **Symptom:** a three-layer quoting chain (`bash -> ssh -> python -c`) mangles quotes,
  strips `$` variables, or silently rewrites the script; measured repeatedly on this fleet.
- **Detect:** any prompt step that says "run: ssh host python -c \"...\"" with a multi-line
  script is a defect.
- **Fix:** write the script to a file, `scp` it, execute the file. The prompt must say this
  when it ships multi-line scripts to a VPS.

**Gate B verdict:** every row whose runtime is touched by the dispatch must be checked or
justified. One unjustified row = PASS-WITH-FIXES; a prompt that structurally repeats a
measured failure (B1 content-through-PS-here-string, B4 cached creds) = REJECT until fixed.

## 6) GATE C - AI-SLOP DETECTION

Slop in a prompt is worse than slop in a document: the child EXECUTES the slop, and the
slop propagates into the deliverable. Run all six detectors on the prompt text. Each has a
mechanical check; no vibes.

### C1 - Padding comments / filler lines

- **Detect:** lines that exist only to add length: repeated comment frames, `<!-- padding -->`
  style blocks, sections that restate the header, bullet lists where every bullet is the
  previous bullet with one word changed.
- **Test:** pick 5 consecutive lines at random from the bottom third of the prompt. If
  deleting them changes nothing observable for the child, they are padding.
- **Campaign provenance:** audit found ~25-30% padding share in generated skills; juries
  deduct for it; the fix is deletion, not rewording.

### C2 - Placeholder URLs / example-only content

- **Detect:** grep for `example.com`, `YOUR_API_KEY`, `<placeholder>`, `TODO`, `TBD`,
  `FIXME`, `xxx`, `lorem`. In a DISPATCHED prompt, a placeholder that the parent was
  supposed to fill is a REJECT - the child cannot fill it and will invent a value.
- **Legitimate exceptions:** an interactsh/OOB callback domain in a pentest payload, a
  deliberately-abstract `{{placeholder}}` the parent fills at dispatch time. Both must be
  MARKED as intentional in the prompt, or they count as slop.

### C3 - Byte-identical templates

- **Detect:** when a wave dispatches several prompts built from one template, hash them.
  If two prompts for DIFFERENT scopes are byte-identical (or identical except the seat
  name), the template's variable slots did not resolve.
  ```
  python -c "import hashlib,sys; [print(hashlib.sha256(open(f,'rb').read()).hexdigest()[:16], sys.argv[1]) for f in sys.argv[1:]]" p1.txt p2.txt
  ```
- **Why it matters:** identical mandates to two children = duplicated work + merge conflicts
  (the dedup rule of the subagents skill violated by construction).

### C4 - Recital-instead-of-fire

- **Detect (applies to prompts that instruct the child to fire skills):** the prompt's gate
  contract must require REAL tool calls, and the parent's plan must include a post-run
  check that counts actual skill tool invocations (e.g. via the session message record:
  tool parts with `name == "skill"` and completed state, deduped by tool-call id).
  A prompt that says "remember to fire the skills" with no verification hook produces
  recital: prose that says "godmode fired" with zero tool calls in the session record.
- **Measured:** the P8 root cause class - page-1-only reads undercounted fires; the
  corrected counter (cursor-following, deduped by tool-call id) is the reference
  implementation for this check.

### C5 - Unverified claims inside the prompt

- **Detect:** any line in the prompt asserting a fact the child cannot verify and the
  parent did not (version numbers, prices, endpoints, "the server is at X", "the file
  contains Y"). Each such claim must either (a) carry its source, or (b) be marked
  `[UNVERIFIED - child must confirm before relying]`.
- **Rule:** a prompt that hands the child a fabricated fact has weaponized hallucination;
  the child will build on it.

### C6 - Slop phrasing / instruction echo

- **Detect:** filler like "as an AI", "in today's fast-paced world", "it is important to
  note that" (uninformative uses), and any instruction telling the child to echo the prompt
  back or narrate its reasoning (known refusal/timeout trigger on reasoning models).
- **Fix:** delete; instructions must be imperative and terminal-tested.

**Gate C verdict:** any C1-C6 hit on a dispatch prompt = the prompt is rewritten (slop is
deleted, not flagged), then re-checked. A second slop pass needed = REJECT; the template
upstream is broken, and per the update rule (Section 10) the template owner gets the note.

## 7) GATE D - SEAT-DISJOINTNESS VALIDATION (tasklist-first)

A dispatch that lands in a seat whose scope overlaps a sibling's is a defect even if the
prompt is otherwise perfect. Preflight enforces tasklist-first:

**Checklist:**

- [ ] A tasklist file EXISTS before this dispatch (written by the orchestrator) - no list,
      no spawn. If the canonical path is unwritable, a fallback run-dir path is cited in
      the plan; preflight verifies the file actually exists at the cited path.
- [ ] Every seat row has: ID, type, IN (explicit scope), OUT (explicit exclusions), named
      deliverable, depends-on, wave.
- [ ] Pairwise disjointness: for every pair of seats in THIS wave, `IN(A) and IN(B) do not overlap` OR a
      named handoff exists in both directions. Each OUT names at least one sibling's IN.
- [ ] Exactly one owner per component: no unassigned remainder of the overall goal, no
      double-claimed file.
- [ ] Wave discipline: this dispatch belongs to the wave the tasklist assigns it; verify
      and adversarial seats are NOT in the same batch as worker seats.
- [ ] The prompt's OUT section names at least one sibling's IN ("do not cover X - seat Y
      owns X"), proving the boundary is real.

**Detect tooling (cheap, deterministic):** extract the IN/OUT lines from each spawned
prompt in the wave, and diff pairwise. Two prompts sharing a file path in IN with no
matching OUT exclusion = finding. This is a 10-line script, not a judgment call.

**Gate D verdict:** any overlap without a named handoff = REJECT the wave dispatch until
scopes are rewritten. A single-seat dispatch still needs IN/OUT/deliverable present
(floor-crew rules apply at the wave level, not inside one prompt).

## 7) GATE E - SELF-CONTAINMENT AND OUTPUT-CONTRACT CHECKS (Gate E, structural)

Beyond the schema and the runtime, the prompt must stand alone and end deterministically:

- [ ] **Standalone:** the child sees ONLY what the prompt carries. No "as discussed", no
      session history pasted in bulk, no reference to "the plan file" without its path.
- [ ] **Shared assumptions pinned:** names, interfaces and conventions the child must not
      renegotiate are stated inside the prompt (pinned before dispatch, identical for all
      siblings).
- [ ] **Goal as acceptance test:** the prompt states the success criterion as something
      runnable/observable ("the script exits 0 and the JSON contains status=PASS"), never
      "make it good".
- [ ] **Final-message contract:** the child is told to end with the fenced JSON block
      `{"status": "...", "deliverable_path": "...", "findings": [], "blockers": [],
      "files_touched": []}` - all keys present, empty arrays allowed - followed by the
      gates line as the very last line.
- [ ] **Evidence rule:** "paste real tool results; mark [UNVERIFIED] what you did not run."
- [ ] **Scope fence:** "Report a blocker in one line; do NOT widen scope; do NOT spawn
      subagents" - present verbatim or equivalent.
- [ ] **No time bombs:** no step depends on wall-clock-only conditions ("check back in 10
      minutes") without a concrete re-check command.
- [ ] **Context hygiene:** the prompt carries only what the scope needs; no credentials.

## 8) THE VERDICT FORMAT (Gate F - the record)

Every preflight run ends with EXACTLY this block, appended to the run log:

```
PREFLIGHT VERDICT
prompt: <path or inline hash-prefix>
sha256[:16]: <hash of exact dispatched text>
runtime: <opencode 2.2.6 serve / local shell / VPS bash / ...>
GATE A (spawn-payload schema): <PASS | n findings> - <one line per finding or "clean">
GATE B (runtime known-failures): <PASS | n findings> - <rows checked or justified N/A>
GATE C (ai-slop): <PASS | n hits, all deleted> - <hits>
GATE D (seat disjointness): <PASS | REJECT> - <pairwise evidence>
GATE E (self-containment): <PASS | n findings>
VERDICT: PASS | PASS-WITH-FIXES (fixes applied: n) | REJECT (blocking rows: ...)
evidence: <commands run + exit codes; a verdict with zero commands is invalid>
```

**Verdict semantics (no middle ground, no vibes):**

| Verdict | Meaning | Allowed next action |
|---------|---------|---------------------|
| PASS | all gates clean, evidence pasted | dispatch as-is |
| PASS-WITH-FIXES | findings were mechanical and have been APPLIED to the prompt text; re-hash recorded | dispatch the FIXED text (never the original) |
| REJECT | structural defect (A1/A4/A6-row-4/6/10, C repeat hit, D overlap, missing inputs) | back to the prompt factory / orchestrator; do NOT dispatch |

Rules:

- A verdict without pasted command output is `Unknown`, and Unknown is a REJECT.
- PASS-WITH-FIXES must list every fix as `FIX: <gate> <change>` - silent fixes are
  forbidden (the orchestrator merges against the recorded verdict).
- A REJECT is not a failure of the pipeline; it is the pipeline working. Rejected prompts
  go back with the finding list, get one rewrite, and re-preflight.

## 9) RE-RUN IDEMPOTENCY + THE UPDATE RULE

**Re-run idempotency:**

1. Preflight is a pure function of (prompt bytes, spawn payload, tasklist, runtime).
   Running it twice on unchanged inputs MUST produce the identical verdict. Any check whose
   outcome depends on wall-clock or session state (A5 post-spawn model assertion) is marked
   `deferred` in the verdict and re-run after the child's first reply - it does not make the
   pre-run verdict unstable.
2. A prompt that already PASSED and is unchanged does not need a full re-run; verify the
   sha256 matches the recorded hash and re-emit the verdict with `idempotent: true`.
   Edited prompt -> hash differs -> full re-run, no exceptions.
3. Pre-flight never mutates the prompt except to APPLY fixes, and every fix is logged.
   An unlogged edit makes the next hash mismatch a REJECT.

**The update rule (new known failures append to the checklist):**

- The moment a dispatch fails in a way this file did not predict, the failure is appended
  to the relevant gate as a new row: same card format (Symptom / Root cause / Detect /
  Fix / Provenance), dated, with the run id.
- Appends are additive; existing rows are never deleted or rewritten (they are the
  mistake-memory). A row found WRONG gets a superseding note, not a silent edit.
- Quarterly (or at campaign close): dedupe pass - two rows with identical Symptom+Fix are
  merged with both provenances kept.
- The update itself follows the ASCII rule (B1): pure ASCII, no em-dashes, no curly quotes,
  or the file corrupts its own future reads.

## 11) ANTI-PATTERNS (automatic defects)

## 12) RUNTIME REGISTRY - extended known-failure table

Gate B's core rows (B1-B6) are the measured minimum. This registry extends them with the
rest of the fleet's runtime surfaces. Rule: a prompt is validated against every runtime it
TOUCHES, judged by the actual dispatch path, not by what the author intended.

| Runtime | Known failure | Detection | Prevention in the prompt |
|---------|---------------|-----------|--------------------------|
| PowerShell 5.1 (any Windows box) | em-dash / curly-quote byte corruption through console or here-strings | byte-level scan: any 0x97 / 0x91-0x94 / 0xE2-0x80 sequences where ASCII expected | ASCII-only content; specify python for non-ASCII writes |
| PowerShell 5.1 | `$ErrorActionPreference='Stop'` + native stderr = NativeCommandError abort | grep the script for `'Stop'` co-occurring with curl/git/ssh/plink | require `$LASTEXITCODE` checks; scope Continue around natives |
| opencode 2.2.6 serve REST | `${VAR}` in prompt prose is NOT expanded at dispatch | grep prompt for `${` outside fenced literal blocks | parent inlines the resolved value before dispatch |
| opencode serve (any version) | password rotates on every restart; cached creds -> mass 401s that look like an outage | credential source in the prompt is anything but "freshest serve log, LAST matching line, read at runtime" | the runtime-read rule, verbatim, in every REST step |
| opencode serve REST | page-1-only reads on cursor-paginated endpoints (50/page) | any step that reads `/message` or a list endpoint without a cursor loop | cursor loop + max-page bound, both stated |
| opencode serve REST | Basic auth vs Bearer confusion (`opencode:<password>`, NOT Bearer) | prompt says "Bearer" or omits the auth scheme | state the exact header once, correctly |
| opencode serve REST | strict `additionalProperties:false` schemas reject extra JSON fields | payload includes convenience fields the schema does not declare | validate payload against the schema shape before send |
| OpenCode spawn depth | children cannot spawn (depth 1, injected DENY on the spawn tool) | any "delegate/spawn/fan out" instruction addressed to the child | child is the implementer; orchestrator owns all spawning |
| OpenCode sessions | `sessionID` resume used where a NEW scope was needed (or parent id passed by accident) | resume with changed mandate text; parent's own id in the resume field | new scope = new spawn; resume only for deeper work in the SAME scope |
| OpenCode models | per-session model override silently diverges from config default | post-spawn model assertion absent from the parent plan | A5 assertion mandatory in every wave plan |
| bash on VPS (scp target) | inline `ssh host python -c "..."` - three quoting layers mangle the script | any `ssh ... python -c` or `ssh host bash -c "..."` with nested quotes in the prompt | scripts go to a file, `scp`, then execute the file |
| bash on VPS | `cmd | tail` / `cmd | head` swallows the checker's exit code | verdict steps that pipe the checker before reading `$?` / `${PIPESTATUS[0]}` | run the checker unpiped for the verdict; pipe only for display |

Provenance discipline: every row above traces to a campaign runlog (D-L3 em-dash byte
patch; P8 cursor pagination; R1 gotchas 5-6; V14CL/V2DGH no-LLM and dual-root findings;
bootstrap-patched PATH warning; probe/relay watcher logs). New rows append here with the
same four columns and a run id.

## 13) DETECTION ONE-LINER LIBRARY (paste-ready)

Every gate check below is runnable as-is. The verdict record must cite which of these ran
and their exit codes. A gate whose check you cannot name is a gate that did not run.

```
# --- Gate A3 / B: cursor-pagination compliance (static scan of the prompt) ---
grep -nE "(/message|/project|/session)" prompt.txt | grep -v cursor    # hits = suspect steps

# --- Gate A4: gates-last contract present exactly once, at the end ---
tail -n 3 prompt.txt                     # the contract line must be visible here
grep -c "gates --" prompt.txt            # expect: exactly 1 (0 or 2+ = reject)

# --- Gate B1: byte-level ASCII scan of the prompt file ---
python -c "d=open(r'prompt.txt','rb').read(); bad=[b for b in d if b>127]; print(len(bad),'non-ascii bytes'); raise SystemExit(1 if bad else 0)"

# --- Gate B1b: em-dash / curly-quote byte fingerprints specifically ---
python -c "d=open(r'f','rb').read(); import sys; sys.exit(1 if (b'\xe2\x80\x94' in d or b'\x97' in d) else 0)"

# --- Gate B3: unresolved ${VAR} in prompt prose (outside fenced blocks) ---
python - <<'EOF'
import re
t=open('prompt.txt',encoding='utf-8',errors='strict').read()
fenced=re.sub(r'```.*?```','FENCED',t,flags=re.S)
hits=re.findall(r'\$\{[A-Za-z_][A-Za-z0-9_]*\}',fenced)
print('unresolved:',hits); raise SystemExit(1 if hits else 0)
EOF

# --- Gate B4: credential-source audit (cached creds are a defect) ---
grep -nE "(password|secret|token|api[_-]?key)" prompt.txt   # then read each hit:
#   OK:   "LAST line matching '^server password ' in freshest /tmp/oc-serve*.log, at runtime"
#   FAIL: a literal credential, or "the password we saved earlier", or an old env file

# --- Gate A2: child-spawn instructions present? ---
grep -inE "\b(spawn|subagent|fan.?out|delegate to)\b" prompt.txt
#   every hit must be past-tense (orchestrator's own action) or a prohibition

# --- Gate C1: padding heuristic (bottom-third line churn) ---
python - <<'EOF'
ls=open('prompt.txt',encoding='utf-8').read().splitlines()
tail=ls[int(len(ls)*0.66):]
blankish=sum(1 for x in tail if len(x.strip())<3)
print(f'bottom-third: {len(tail)} lines, {sum(1 for x in tail if x.strip().startswith("<!--"))} pure comment lines')
EOF

# --- Gate C3: template-collision hash across a wave's prompts ---
python - <<'EOF'
import hashlib,glob
for f in sorted(glob.glob('wave7-seat*.txt')):
    print(f, hashlib.sha256(open(f,'rb').read()).hexdigest()[:16])
EOF
#   two identical hashes = two seats got the same prompt = dedup violation, stop the wave

# --- Gate D: pairwise IN/OUT overlap (deterministic check) ---
python - <<'EOF'
import re,glob
def scope(t,k):
    m=re.search(rf'^{k}:\s*(.+)$',t,re.M|re.I); return set(re.findall(r'[\w/.-]+',m.group(1).lower())) if m else set()
ps={f:(scope(open(f).read(),'IN'),scope(open(f).read(),'OUT')) for f in glob.glob('wave*-seat*.txt')}
fs=list(ps)
for i in range(len(fs)):
    for j in range(i+1,len(fs)):
        (i1,o1),(i2,o2)=ps[fs[i]],ps[fs[j]]
        common=i1&i2-unio(o1,o2) if False else (i1&i2)-o1-o2
        if common: print('OVERLAP',fs[i],fs[i],common)
EOF

# --- Post-dispatch (A5): child actually ran on the requested model ---
# (parent-side check, recorded in the verdict as the model-assertion row)
#   GET /api/session/{sid} -> compare model string against the spawn's requested ref
```

Notes on the one-liners:

- The Gate D snippet is deliberately naive (token-set overlap). It is a TRIPWIRE, not a
  proof: a clean tripwire does not prove disjointness, but ANY hit proves a defect. When it
  fires, fix the scopes; when it is clean, the orchestrator still owns the eyeball pass.
- Every snippet exits non-zero on failure. If you pipe it into something that eats the exit
  code, you have re-created the exact failure class this skill exists to catch (rule: run
  the checker, THEN pipe for display; never judge through the pipe).

## 14) POSITION IN THE STACK (integration contract)

| Neighbor | Contract with this skill |
|----------|--------------------------|
| `/prompt` (the factory) | factory OUTPUT is preflight INPUT. The factory self-scores against its rubric; preflight re-checks against the runtime-failure checklist, which the factory does not know. Both gates run; neither substitutes for the other. |
| `subagents` (orchestrator) | preflight runs BETWEEN the tasklist write and the first spawn of each wave. Wave N's prompts that fail Gate D are fixed BEFORE any seat of wave N launches - a wave launched with overlapping scopes cannot be un-launched cheaply. |
| `session-monitor-auto` | preflight verdict records (prompt hash + verdict) are what the watchdog beats verify against: a child whose output contract says "gates last" can be machine-checked at every beat. |
| `recovery-engineers` | every corrective prompt a recovery seat designs MUST pass preflight before the repair spawn. Recovery loops that skip preflight re-dispatch the same defect (the #1 repair-wave failure). |
| `honestscore` | a dispatch that never preflighted cannot claim the verification dimension: the honestscore evidence list must cite the preflight verdict record. |
| `ideas` | a REJECT with a novel failure class is an ideas trigger: diverge on WHY the factory produced it, not just on the one prompt. |
| brain runbooks | new Gate B registry rows (Section 12) get mirrored into the relevant brain root-cause note on the next sync - this file is the operational checklist, the brain is the memory. |

Timing rule: preflight is cheap (grep + byte scans + pairwise diff, no LLM calls) and runs
in seconds. There is no budget excuse for skipping it. An LLM-costly loop (ideas,
deep-thinker) runs only when preflight finds a defect whose fix needs design, not deletion.

## 15) WORKED EXAMPLE 2 - a bad WAVE dispatch (Gate D failure)

**Scenario:** the orchestrator builds a 3-seat wave from one template. The tasklist says:
seat W1 owns "reconcile results JSONs"; seat R2 owns "verify union counts"; seat A1 is the
adversarial pass. The three dispatched prompts, hash-checked:

```
wave9-seat1.txt  sha256[:16] = 4b1e...   IN: results reconciliation, union counts
wave9-seat2.txt  sha256[:16] = 4b1e...   (byte-identical to seat 1)
wave9-seat3.txt  sha256[:16] = 7d33...   IN: everything (adversarial: "find problems")
```

### Preflight findings

1. **C3 template collision (serious):** seats 1 and 2 hashed identical. The template's
   variable slots did not resolve - both children will reconcile the same files. Merge will
   conflict or, worse, silently double-count.
2. **D scope overlap (serious):** the adversarial seat's IN is "everything" - no OUT, no
   sibling list. Against the de-correlation rule, an adversary with no boundary invents
   findings and burns the verify reserve re-litigating the other seats' scopes.
3. **A4 violation (moderate):** the template's gates line sits mid-prompt, followed by a
   "signature" block. Gate-scan will mis-parse all three finals.
4. **A3 violation (serious):** the verify seat's step 2 says "confirm all messages show the
   gate fire" - no cursor loop. On any session over 50 messages this is a false verdict.

### Fixes applied (all in one pass, then re-hash)

- Seat 1 keeps `IN: results reconciliation`; `OUT: union counts (seat 2 owns them)`.
- Seat 2 rewritten with its own mandate text + sibling list ("do not touch reconciliation
  outputs"); hash now distinct.
- Adversary seat rewritten with the explicit boundary: "only the merged artifact + the
  original spec; do not re-open seat scopes."
- Output contract edited: gates line moved to the true last line; signature block removed.
- Step 2 rewritten: "cursor-paginated read, follow `cursor.next`, cap 200 pages, counts
  computed across all pages."

### Re-verified verdict

```
PREFLIGHT VERDICT (wave 9, re-run after fixes)
sha256[:16] pre-fix  4b1e...  -> post-fix  c81a...
GATE A: PASS (A1 model asserted in plan; A2 no child-spawn verbs; A3 cursor loops present;
         A4 gates-last verified by tail -3; A5 model assertion row present in wave plan)
GATE B: PASS (byte scan 0 non-ascii; no $ErrorActionPreference=Stop; 0 unresolved ${VAR};
            credential rule verbatim present)
GATE C: PASS (template collision resolved; 0 TODO/placeholder; no unverified claims left)
GATE D: PASS (IN-sets pairwise disjoint; each OUT names a sibling IN; adversary separated)
VERDICT: PASS (re-run idempotent: identical verdict on second run, hash-recorded)
```

Note what the example demonstrates about the update rule: the wave-template collision (C3
across seats, not just within one prompt) was NOT in the original checklist. It was added
to Gate C as row C3-bis ("hash across the wave, not within one prompt") with the run id -
that is the update rule working as designed.

## 16) WORKED EXAMPLE 3 - validating a REPAIR-WAVE corrective prompt

Repair prompts (authored by `recovery-engineers`) fail differently from first-run prompts:
they carry failure context, and that context is where the extra failure modes live. The
repair-specific preflight addendum:

- [ ] The corrective prompt names the ORIGINAL defect in one sentence (evidence-linked),
      not a vague "try harder" - a repair prompt without a stated root cause is rejected.
- [ ] It lists what was already tried (so the repair seat does not repeat it), including
      the last 3 attempts verbatim or by path.
- [ ] It names the surviving artifacts that must NOT be regenerated (dedup rule) - a
      repair prompt that re-runs successful seats destroys verified work.
- [ ] It narrows scope: the repair seat's IN is the failing sub-scope only; its OUT
      explicitly excludes every seat that passed.
- [ ] It restates the runtime rules that the original prompt got wrong (if the original
      failure WAS a Gate A/B item, the repair prompt quotes the corrected form explicitly).
- [ ] It sets the loop bound: the repair seat knows the abort criterion (15 identical-error
      loops -> abort and report) so it fails loudly instead of grinding silently.

A corrective prompt that fails any line above gets `PASS-WITH-FIXES` at best, and the fix
is applied before the repair spawn - never "dispatch as-is and see".

## 17) VERDICT RECORD SCHEMA (machine-readable form)

For fleet tooling that parses preflight records, the verdict ALSO lands as JSON alongside
the human-readable block. Both must agree; a disagreement is a defect in the recorder.

```json
{
  "kind": "prompt-preflight-verdict",
  "prompt_hash": "sha256-prefix-16",
  "runtime": ["opencode-2.2.6-serve", "bash-vps"],
  "gates": {
    "A_spawn_payload": {"verdict": "PASS", "findings": []},
    "B_runtime":       {"PASS": ["B1","B2","B3","B4"], "findings": []},
    "C_slop":          {"PASS": true, "hits": []},
    "D_seats":         {"PASS": true, "pairs_checked": 3, "overlaps": []},
    "E_self_contained":{"PASS": true, "findings": []}
  },
  "verdict": "PASS",
  "fixes_applied": [],
  "evidence": ["byte-scan: 0 non-ascii", "grep gates -- count=1", "pairwise-diff: clean"],
  "run_id": "<wave or run identifier>",
  "timestamp_utc": "<iso8601>"
}
```

Rules: `verdict` values are only PASS / PASS-WITH-FIXES / REJECT. `fixes_applied` must be
empty for PASS and non-empty for PASS-WITH-FIXES. A REJECT record lists, per gate, the
failed check and the command that demonstrated it. The recorder never rounds, never
upgrades a verdict without a re-run, and appends the same record to the runlog.
